# BatchGuard 代码规范（C++20）

> 状态：v0.1 草案。目标是让代码容易阅读、测试和解释，不追求形式上的复杂。

## 1. 基本原则

- 正确性和可读性优先于炫技。
- 用类型表达约束，避免依赖注释补救模糊设计。
- 一个函数只承担一个清晰职责。
- 优先值语义和 RAII，不手工管理资源生命周期。
- 只使用能解决实际问题的 C++20 特性。

## 2. 语言与构建

- 语言标准固定为 C++20，关闭编译器扩展。
- 源文件统一使用 UTF-8。
- Debug 和 Release 都必须能够构建。
- 新增警告不得被忽略；禁止通过全局关闭警告掩盖问题。
- 构建产物只能放在源码目录之外的 build 目录。

## 3. 格式

- 缩进使用 4 个空格，不使用 Tab。
- 左花括号与声明放在同一行。
- 建议单行不超过 100 个字符；长参数按语义换行。
- 头文件使用 `#pragma once`。
- 每个文本文件以换行结尾。
- 后续用 `.clang-format` 固化格式，规则经双方确认后再添加。

## 4. 命名

| 对象 | 规则 | 示例 |
|---|---|---|
| 类、结构体、枚举 | `PascalCase` | `FileRecord` |
| 函数、方法 | `lowerCamelCase` | `scanDirectory` |
| 局部变量、参数 | `lowerCamelCase` | `rootPath` |
| 私有成员 | `lowerCamelCase_` | `records_` |
| 编译期常量 | `kPascalCase` | `kReadBufferSize` |
| 命名空间 | `snake_case` | `batchguard` |
| 文件名 | `snake_case` | `file_scanner.cpp` |

- 名称应表达业务含义，避免 `data`、`temp`、`obj` 等模糊命名。
- 布尔值使用 `is`、`has`、`can`、`should` 等前缀。

## 5. 头文件与依赖

- include 顺序：当前头文件、C++ 标准库、第三方库、项目头文件。
- 各组之间空一行，同组按字母排序。
- 头文件中禁止 `using namespace`。
- 能前向声明时可前向声明，但不能牺牲可读性。
- 公共头文件不得依赖应用层或界面层。
- 不在头文件中放无必要的实现，模板与短小内联函数除外。

## 6. 接口设计

- 单参数构造函数默认使用 `explicit`。
- 不修改对象状态的方法使用 `const`。
- 调用方不应忽略的重要返回值使用 `[[nodiscard]]`。
- 确实不会抛异常的函数使用 `noexcept`，不机械添加。
- 优先返回对象，不用输出参数同时返回多个结果。
- 避免过长参数列表；相关参数应组合为有含义的结构体。
- 枚举使用 `enum class`。

## 7. 所有权与生命周期

- 默认使用栈对象和值语义。
- 独占动态资源使用 `std::unique_ptr`。
- 只有确实存在共同所有权时才使用 `std::shared_ptr`。
- 裸指针和引用只表示非拥有关系，且不得超过被引用对象生命周期。
- 禁止直接使用 `new`、`delete`、`malloc` 和 `free`。
- 文件、线程和锁必须由 RAII 对象管理。

## 8. 错误处理

- 文件不存在、权限不足等预期失败必须显式返回，不得静默忽略。
- 文件系统操作优先使用带 `std::error_code` 的接口，避免一次失败终止整批任务。
- 捕获异常后必须补充上下文或在应用边界统一转换，禁止空 `catch`。
- `assert` 只检查程序员错误，不用于处理用户输入或运行时失败。
- 日志不得包含敏感路径、凭据或公司业务数据。

## 9. 并发

- 第一版功能正确后再引入并发。
- 优先使用 `std::jthread` 和 `std::stop_token` 管理取消与线程退出。
- 禁止分离线程；每个线程都必须有明确所有者和结束路径。
- 共享可变状态必须说明同步方式，优先通过消息或结果传递减少共享。
- 持锁期间不执行文件 I/O、日志回调或未知外部代码。

## 10. 测试

- 核心逻辑必须能脱离 CLI 和未来 GUI 单独测试。
- 每个测试只验证一个行为，名称说明场景和预期。
- 文件测试使用临时目录和测试运行时生成的数据。
- 测试不得依赖执行顺序、固定盘符或个人机器路径。
- 修复缺陷前先补充能够复现问题的测试。

## 11. 明确禁止

- 全局可变状态。
- C 风格强制转换。
- 魔法数字和散落的路径常量。
- 为简单问题引入复杂继承层次。
- 在 `main.cpp` 中堆积业务实现。
- 未经讨论新增第三方依赖。
