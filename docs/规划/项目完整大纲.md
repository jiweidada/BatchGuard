## 1. 项目概览

### 1.1 项目名称

`BatchGuard`

### 1.2 项目定位

BatchGuard 是一个使用 C++20 开发的本地文件检查工具。用户提供一个目录后，
程序递归扫描普通文件，根据文件内容识别重复项，记录无法处理的文件，并输出可验证的报告。

### 1.3 核心原则

- 安全：默认只读，不删除、移动、重命名或修改用户文件。
- 正确：文件名不参与重复判断，重复关系以文件内容为准。
- 可解释：模块、数据流、错误和测试都能由开发者独立说明。
- 可演进：先完成纯 C++ 核心和 CLI，再考虑并发、导出和 GUI。
- 小步交付：每个增量都能构建、验证和审查。

## 2. 项目成功后的样子

MVP 完成后，用户可以在 Windows 终端运行：

```text
BatchGuard "E:\待整理目录"
```

程序会：

1. 验证输入目录。
2. 递归发现普通文件。
3. 读取文件大小并筛选可能重复的候选文件。
4. 对候选文件计算内容指纹。
5. 建立重复文件组。
6. 输出统计、重复组和失败记录。
7. 通过退出码表达执行结果。

项目交付的不只是一个可执行文件，还包括自动化测试、构建说明、设计文档和清晰的 Git 历史。

## 3. 产品范围

### 3.1 MVP 必须包含

- 单目录输入。
- Windows 中文及空格路径支持。
- 递归扫描普通文件。
- 文件大小候选分组。
- SHA-256 内容指纹。
- 重复文件分组。
- 单文件失败隔离。
- 中文控制台报告。
- 明确退出码。
- 自动化测试。

### 3.2 MVP 明确不包含

- Qt 或其他图形界面。
- 删除、移动、重命名及自动清理。
- CSV、JSON 等报告文件导出。
- 数据库与历史扫描记录。
- 网络目录、云存储和实时监控。
- 暂停、恢复和取消。
- 多线程或复杂线程池。

### 3.3 MVP 完成后的候选功能

候选功能按以下顺序单独评估，不自动进入开发：

1. 进度统计与安全取消。
2. 并发计算内容指纹。
3. CSV 或 JSON 报告导出。
4. 扫描规则与扩展名过滤。
5. Qt 图形界面。
6. 扫描结果对比与历史记录。

## 4. 用户流程

### 4.1 正常流程

```text
启动程序
  → 输入目录
  → 验证通过
  → 扫描文件
  → 计算内容指纹
  → 建立重复组
  → 输出报告
  → 返回成功退出码
```

### 4.2 输入错误流程

```text
启动程序
  → 参数缺失或路径无效
  → 输出使用方法和错误原因
  → 不开始扫描
  → 返回输入错误退出码
```

### 4.3 局部失败流程

```text
扫描过程中某个文件失败
  → 记录文件路径、失败阶段和原因
  → 继续处理其他文件
  → 最终输出完整报告
  → 返回部分失败退出码
```

## 5. 功能模块

模块名称描述职责，不代表最终类名已经确定。

| 模块 | 主要职责 | MVP 优先级 |
|---|---|---:|
| 命令行入口 | 读取参数、展示帮助、返回退出码 | P0 |
| 输入验证 | 检查路径是否存在且为目录 | P0 |
| 文件发现 | 递归枚举普通文件并记录发现阶段错误 | P0 |
| 元数据读取 | 获取路径、文件大小等基础信息 | P0 |
| 候选分组 | 先按文件大小筛选可能重复的文件 | P0 |
| 内容指纹 | 分块读取并生成 SHA-256 | P0 |
| 重复分组 | 根据大小和指纹生成重复组 | P0 |
| 报告汇总 | 汇总数量、重复组和失败项 | P0 |
| 控制台展示 | 按固定顺序输出中文报告 | P0 |
| 日志系统 | 运行日志和诊断信息 | MVP 后 |
| 并发调度 | 多文件并发、取消与资源限制 | MVP 后 |
| 图形界面 | 目录选择、表格、进度和筛选 | MVP 后 |

## 6. 技术架构

### 6.1 分层

```text
命令行应用层
    │
    │ 调用
    ▼
核心用例层
    │
    ├── 文件发现
    ├── 内容指纹
    ├── 重复分组
    └── 报告汇总
    │
    ▼
操作系统与文件系统
```

### 6.2 依赖规则

- `batchguard_cli` 可以依赖 `batchguard_core`。
- 测试可以依赖 `batchguard_core`。
- `batchguard_core` 不得依赖 CLI 或未来 GUI。
- CLI 只负责输入输出，不保存核心业务规则。
- 文件系统和哈希实现应与报告展示解耦。
- 新增第三方依赖前必须单独讨论其必要性、许可证和部署成本。

### 6.3 CMake 目标

MVP 计划使用：

| 目标 | 类型 | 作用 |
|---|---|---|
| `batchguard_core` | 静态库 | 文件扫描、内容指纹、重复分组和报告 |
| `batchguard_cli` | 可执行程序 | 命令行输入输出与退出码 |
| `batchguard_tests` | 测试程序 | 单元测试和集成测试 |

详细目录见 [项目结构.md](../设计/项目结构.md)。

## 7. 核心数据流

```text
目录路径
  ↓
扫描请求
  ↓
文件列表 + 发现失败项
  ↓
按文件大小形成候选组
  ↓
候选文件内容指纹
  ↓
重复文件组 + 处理失败项
  ↓
扫描报告
  ↓
控制台输出 + 退出码
```

重要约束：

- 每个阶段接收明确输入并产生明确结果。
- 预期的文件错误进入报告，不通过全局异常中断批次。
- 展示层只读取报告，不重新判断业务规则。
- 输出顺序保持稳定，确保测试结果可重复。

## 8. 候选领域对象

以下只是设计讨论中的概念，接口阶段再确定正式名称和字段：

| 概念 | 可能包含的信息 |
|---|---|
| 扫描请求 | 根目录、递归规则 |
| 文件记录 | 路径、大小、内容指纹、处理状态 |
| 失败记录 | 文件路径、失败阶段、错误原因 |
| 重复文件组 | 组编号、文件大小、内容指纹、成员列表 |
| 扫描报告 | 总数、成功数、失败项、重复组、完成状态 |

设计时优先使用值语义；是否需要动态多态、智能指针或接口抽象必须由实际需求证明。

## 9. C++20 能力映射

项目会自然使用以下能力：

| C++ 能力 | 使用位置 |
|---|---|
| RAII | 文件流、Windows 句柄和工作线程的自动释放 |
| `std::filesystem` | 路径验证、目录遍历和文件元数据 |
| `std::error_code` | 可恢复的文件系统失败 |
| `std::optional` | 确实可能不存在的单一结果 |
| `std::variant` | 需要表达有限状态结果时再评估 |
| Ranges | 能提升集合处理可读性时使用 |
| `std::span` | 非拥有连续缓冲区视图 |
| `enum class` | 文件状态、失败阶段和退出状态 |
| `std::jthread` / `std::stop_token` | MVP 后的并发与取消 |

不为了覆盖语法清单而强行使用 Concepts、模板元编程或复杂继承。

## 11. 测试策略

### 11.1 单元测试

重点验证：

- 输入验证。
- 候选分组。
- 重复分组。
- 报告统计。
- 退出码映射。

### 11.2 集成测试

重点验证：

- 目录到最终报告的完整流程。
- 空目录和嵌套目录。
- 同内容不同名称。
- 同大小不同内容。
- 零字节文件。
- 中文和空格路径。
- 文件读取失败后继续处理。

### 11.3 测试数据

- 由测试在临时目录中生成。
- 测试结束后由 RAII 自动清理。
- 不使用固定盘符。
- 不包含公司、客户或个人业务数据。

完整 MVP 用例见 [第一版MVP.md](第一版MVP.md)。

## 12. 错误与退出策略

错误分为三类：

| 类型 | 示例 | 处理 |
|---|---|---|
| 输入错误 | 参数缺失、目录不存在 | 不扫描，输出原因 |
| 局部文件错误 | 文件消失、拒绝访问 | 记录后继续 |
| 致命内部错误 | 无法维持程序基本状态 | 统一捕获并结束 |

退出码暂定：

- `0`：扫描完成且所有发现文件处理成功。
- `1`：命令行或输入目录错误。
- `2`：扫描完成但存在局部文件失败。
- `3`：不可恢复的内部错误。

重复文件本身不是程序错误。

## 13. 非功能要求

### 安全

- MVP 对被扫描目录保持只读。
- 不自动执行清理操作。
- 报告不包含文件内容。

### 可维护

- 核心逻辑与展示层分离。
- 函数和类型遵守 [代码规范.md](../设计/代码规范.md)。
- 每次功能变更同步测试和相关文档。

### 性能

- 文件内容采用固定大小缓冲区分块读取。
- 先按文件大小筛选，避免对明显不重复的文件计算指纹。
- MVP 基线优先保证正确性；完整回归后再以独立阶段引入有界并发。

### 可移植

- MVP 首先支持 Windows。
- 核心代码尽量使用标准 C++20。
- Windows 专属能力集中封装，避免散落在业务代码中。

## 14. 协作与审查方式

每个阶段遵循：

1. 先说明当前小目标、设计和验收方法。
2. 双方确认后再写代码。
3. 单次尽量只改 1～3 个文件。
4. 完成后展示 diff、构建结果和测试结果。
5. 基哥阅读、提问或修改。
6. 只有收到明确“继续”才进入下一增量。
7. 未经确认不自动提交 Git。

如果实现暴露出设计问题，先回到文档修正规则，再继续编码。

## 16. 主要风险

| 风险 | 应对 |
|---|---|
| 范围不断扩大 | 坚持 MVP 边界，新功能单独评审 |
| 一开始过度抽象 | 先用具体实现验证职责，再提取接口 |
| 哈希方案引入过重依赖 | 在实现前比较系统接口、轻量库和部署成本 |
| Windows 中文输出乱码 | 在 CLI 设计阶段单独验证编码策略 |
| 文件扫描期间内容变化 | 明确结果语义并记录读取失败 |
| 测试依赖本机环境 | 使用临时目录和运行时生成数据 |
| 代码由 AI 一次性生成 | 强制小步审查，开发者能解释后才继续 |

## 17. 进入编码前仍需确认

1. 是否接受 MVP 只支持 Windows。
2. 是否接受中文控制台输出。
3. 是否接受默认递归扫描全部普通文件。
4. 是否接受“文件大小 + SHA-256”的重复判断。
5. SHA-256 采用哪种实现方式。
6. 测试框架使用标准 CTest、自建断言还是第三方框架。
7. 第一笔骨架改动的具体文件清单。

前四项属于产品行为，第五至第七项属于技术设计。产品行为确认后，再进入技术选型。
