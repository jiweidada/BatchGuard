## 1. 版本目标

BatchGuard v0.2.0 在保留 v0.1.0 命令行程序和只读安全边界的基础上，新增一个
Windows Qt Widgets 桌面界面。用户可以选择目录、设置哈希线程数、观察扫描进度、
取消扫描，并通过简洁的结论摘要、重复组详情和失败项查看扫描分析结果。

本版本是 v0.1.0 的桌面交互增量，不是架构重写，因此版本号使用 `0.2.0`，不直接
跳到 `2.0.0`。

## 2. 已知环境与技术选择

### 2.1 本机 Qt 环境

本机已经安装 Qt 5.14.2：

```text
E:\Qt\Qt5.14.2
```

可用的 64 位桌面套件包括：

```text
E:\Qt\Qt5.14.2\5.14.2\msvc2017_64
E:\Qt\Qt5.14.2\5.14.2\mingw73_64
```

当前 BatchGuard 使用 MSVC 14.29 和 Ninja 构建，因此 v0.2.0 首选
`msvc2017_64` 套件，不切换到 MinGW。当前命令行可见的 CMake 实际版本为
`4.2.0-rc1`。阶段 10 必须先验证 Qt 5.14.2、当前 MSVC、Ninja 和 CMake 的实际
配置、链接及运行兼容性，验证通过后才进入界面开发。

已完成以下只读环境检查：

- Qt 目录中存在 Debug、Release `Qt5Widgets` 库。
- Qt 目录中存在 Debug、Release `qwindows` 平台插件。
- 普通 PowerShell 当前没有直接找到 `cl.exe` 和 `ninja.exe`。
- 现有 CLion 构建缓存使用 MSVC 19.29 和 CLion 自带 Ninja。

因此阶段 10 优先使用 CLion CMake Profile，或在正确加载 MSVC 与 Ninja 的开发
终端中验证。不得为了让普通终端临时可用而把本机工具绝对路径写入项目 CMake。

### 2.2 Qt 版本策略

- v0.2.0 首先使用现有 Qt 5.14.2，降低环境准备成本。
- Qt 5.14.2 已进入官方文档归档，不作为长期维护版本承诺。
- 如果兼容性验证失败，不在业务代码中堆积临时补丁，应单独评估升级 Qt 6。
- Qt 版本升级属于独立依赖变更，不与窗口功能混在同一提交。

Qt 5.14 文档入口：

- <https://doc.qt.io/archives/qt-5.14/>

### 2.3 依赖接入规则

Qt 是开发机安装的外部 SDK，通过 CMake `find_package()` 接入，不把整套 Qt
二进制或源码复制到 `Third_Party/`。`Third_Party/` 继续只保存需要随仓库固定版本
管理的第三方源码。

Qt 只链接 GUI 相关目标，`batchguard_core`、CLI 和不需要界面的核心测试不得产生
Qt 依赖。没有安装 Qt 的环境仍应能关闭 GUI 选项并构建 v0.1.0 的 CLI 和核心测试。

```text
├──────────────────────────────────────────────────────────────┤
│ 当前阶段：计算内容指纹                    [取消扫描]         │
│ [████████████████░░░░░░░░] 68%                              │
│ 已完成 1666/2991 个文件，19732465623/96487831127 字节        │
├──────────────────────────────────────────────────────────────┤
│ 扫描完成：检查 4077 个文件，发现 18 组重复内容，             │
│ 涉及 46 个文件，理论可节省 23.4 GB；8 个文件未完整处理。     │
│ 已扫描 4077 │ 成功 4069 │ 冗余副本 28 │ 可节省 23.4 GB      │
├──────────────────────────────────────────────────────────────┤
│ [重复文件] [处理失败]                                        │

│ 1    │ 3      │ 2.3 GB     │ 2        │ 4.6 GB              │

└──────────────────────────────────────────────────────────────┘
```

界面第一版优先使用系统原生样式和布局管理器，不使用固定像素位置。主窗口应能在
Windows 100%、125% 和 150% 缩放下正常使用。

结果区域遵循“先结论、后汇总、再展开详情”的渐进展示原则：

- 主界面只保留最重要的扫描数量、重复组、冗余副本、理论可节省空间和失败数量。
- 候选文件数、候选字节数、哈希完成数、扫描耗时和精确字节数进入扫描详情或
  工具提示，不与主要结论争夺视觉空间。
- SHA-256 默认隐藏，仅用于诊断或复制，不作为普通用户识别重复组的主要信息。
- 完整路径只在所选重复组的详情区域显示，主表不重复显示相同组信息。
- 复制路径和打开所在目录使用右键菜单，避免持续占用主界面空间。

四阶段进度映射如下：

| 阶段 | 进度条 | 详情文本 |
|---|---|---|
| 发现 | 总数未知时使用忙碌模式 | 累计发现文件数 |
| 元数据 | 按完成文件数映射 | 完成数/总数 |
| 哈希 | 优先按字节映射，零字节候选按文件数映射 | 文件数和 64 位字节数 |
| 分组 | 开始时忙碌，完成时 100% | 正在生成或已经完成 |

`QProgressBar` 只接受 `int`，不能直接接收可能很大的字节数。界面统一把真实比例
映射到固定刻度，例如 `0` 至 `1000`，详情文本继续显示核心提供的 64 位原始数值。

## 5. 应用状态与交互规则

GUI 使用显式状态控制控件，不通过多个互相独立的布尔值拼接状态：

```text
Idle
  └──> Scanning
         ├──> Cancelling ──> Cancelled
         ├──> Completed
         └──> Failed
```

各状态行为如下：

| 状态 | 目录和线程设置 | 开始按钮 | 取消按钮 | 结果 |
|---|---|---|---|---|
| `Idle` | 可用 | 有效目录时可用 | 禁用 | 保留上次完整结果 |
| `Scanning` | 禁用 | 禁用 | 可用 | 清空旧结果并显示进度 |
| `Cancelling` | 禁用 | 禁用 | 禁用 | 显示“正在取消” |
| `Completed` | 可用 | 可用 | 禁用 | 显示本次完整结果 |
| `Cancelled` | 可用 | 可用 | 禁用 | 不把部分结果标为完整 |
| `Failed` | 可用 | 可用 | 禁用 | 显示可理解的错误信息 |

交互约束：

- 同一时刻最多执行一次扫描。
- 扫描过程中不能修改根目录或哈希线程数。
- 点击取消只发出协作式停止请求，不强制终止线程。
- 用户关闭正在扫描的窗口时，先请求停止，再等待后台扫描安全退出。
- 不使用 detached thread，不允许后台线程在窗口销毁后继续访问 GUI 对象。
- 取消后的部分重复组不能作为完整结果展示，避免用户误判。

## 6. 目标架构

### 6.1 CMake 目标

计划新增以下目标：

| 目标 | 类型 | 职责 |
|---|---|---|
| `batchguard_gui_support` | 静态库 | 主窗口、控制器、模型和 Qt 适配 |
| `batchguard_gui` | GUI 可执行程序 | 创建 `QApplication` 并组装窗口 |
| `batchguard_gui_tests` | 测试程序 | Qt 状态、信号和数据模型测试 |

完整依赖方向：

```text
batchguard_cli ───────> batchguard_cli_support ───────> batchguard_core

batchguard_gui ───────> batchguard_gui_support ───────> batchguard_core
                                      │
                                      └───────────────> Qt5::Widgets

batchguard_tests ─────────────────────────────────────> batchguard_core
batchguard_gui_tests ─> batchguard_gui_support ───────> Qt5::Test
```

约束：

- `batchguard_core` 不包含 `QObject`、`QString`、信号或槽。
- CLI 不依赖 GUI，GUI 不依赖 CLI 展示代码。
- 核心报告继续使用标准 C++ 类型。
- GUI 适配层负责标准 C++ 路径、错误和报告到 Qt 展示类型的转换。
- `apps/gui/main.cpp` 只创建应用和主窗口，并进行最外层异常兜底。

### 6.3 UI 层职责

UI 层采用“薄视图、单一控制器、后台工作对象、只读模型”：

```text
MainWindow
    │ 用户命令和状态展示
    ▼
ScanController（GUI 线程中的唯一状态源）
    │                    ├── ResultSummary
    │                    ├── DuplicateGroupModel
    │                    ├── DuplicatePathModel
    │                    └── FailureModel
    ▼
QThread + ScanWorker
    │ 同步调用、转发进度
    ▼
batchguard_core
```

- `MainWindow` 只读取控件输入、转发用户命令并渲染控制器状态，不直接扫描目录。
- `ScanController` 维护应用状态、输入有效性、一次扫描的线程和取消源。
- `ScanWorker` 在一个专用 `QThread` 中同步调用核心，并捕获所有致命异常。
- `ResultSummary` 从完整且不可变的核心报告生成摘要数据和界面结论。
- 表格模型只读取不可变报告，不重新实现重复判断、失败分类等核心业务规则。
- 模型、控件和所有 `QObject` 界面状态只在 GUI 主线程更新。
- `apps/gui/main.cpp` 只创建 `QApplication`、组装对象并进行最外层异常兜底。

为便于阶段 12 使用可控假扫描验证状态，`ScanController` 与真实核心调用之间保留
可替换的扫描执行边界。测试可以注入假执行对象，不需要扫描真实大目录，也不通过
公开私有槽函数来伪造状态。

## 7. 扫描线程与取消设计

### 7.1 线程分工

一次 GUI 扫描包含以下线程：

```text
GUI 主线程
  │
  │ 队列信号：开始、进度、完成、失败
  ▼
一个扫描工作线程
  │
  │ 同步调用 batchguard_core
  ▼
核心哈希调度器
  └── 最多 N 个现有 std::jthread 哈希工作线程
```

- GUI 主线程只处理控件、模型和窗口事件。
- 扫描工作线程调用现有同步 `scanDirectory()`，避免阻塞 GUI 事件循环。
- 核心继续负责文件级有界并发，GUI 不创建“一文件一线程”。
- 核心进度回调仍在扫描调用线程串行执行。
- 工作线程通过 Qt queued connection 把进度发送回 GUI 主线程。
- 所有 `QAbstractItemModel` 更新都在 GUI 主线程完成。
- 工作线程传回 `std::shared_ptr<const ScanReport>` 或等价的不可变结果句柄，避免
  跨线程深拷贝大量路径。
- 自定义跨线程类型只在 GUI 适配层注册为 Qt 元类型，核心头文件不引入 Qt 宏。

### 7.2 核心取消能力

现有 `scanDirectory()` 没有外部停止参数。内部 `std::stop_source` 只用于哈希工作线程
异常处理，`QThread::requestInterruption()` 不能自动停止纯 C++ 核心，因此必须先
扩展核心取消语义。

计划使用 C++20 `std::stop_token`：

- 扫描控制器持有一次扫描对应的 `std::stop_source`。
- 核心扫描接口接收 `std::stop_token`。
- 文件发现循环定期检查停止请求。
- 元数据循环在领取下一个文件前检查停止请求。
- 哈希调度器收到停止请求后不再领取新任务。
- 单文件哈希每读取一个 64 KiB 数据块后检查停止请求。
- 重复分组开始前检查停止请求。
- `std::jthread` 通过 RAII 完成回收，不强制杀死线程。

取消请求不能只实现为发送给 `ScanWorker` 的 queued slot。工作对象同步执行核心
扫描时，其线程事件循环不能及时处理普通队列调用。`ScanController` 必须直接调用
线程安全的 `std::stop_source::request_stop()`，而工作对象只读取对应令牌。

扫描中关闭窗口时采用异步关闭流程：窗口先忽略本次关闭事件、请求停止并进入
`Cancelling`，待扫描线程退出后再完成关闭。GUI 线程不得为了关闭窗口长时间
阻塞等待，不能使用 detached thread，也不能让工作对象在窗口销毁后继续发送状态。

扫描结果需要区分：

- 正常完成且无文件失败。
- 正常完成但有局部文件失败。
- 用户取消。
- 不可恢复的内部失败。

具体接口名在阶段 11 设计评审时确定。无论采用 `ScanCompletion` 字段还是单独结果
类型，都必须保证取消状态不会被 `failures.empty()` 误判为完整成功。

### 7.3 进度事件控制

现有核心会在哈希读取块完成后持续报告进度。为避免大文件扫描产生过多 Qt 队列
事件，`ScanWorker` 负责对普通进度更新做时间节流：

- 默认最多约每 100 ms 向 GUI 发送一次普通进度。
- 阶段变化、阶段完成、扫描完成、取消和失败事件不得被节流丢弃。
- 控制器只接受当前扫描标识对应的事件，忽略已经结束的旧扫描事件。
- GUI 进度始终单调，不能因晚到事件从新阶段退回旧阶段。

## 8. 结果模型

### 8.1 信息层级

完整扫描首先生成一句自然语言结论，例如：

```text
扫描完成：检查 4077 个文件，发现 18 组重复内容，涉及 46 个文件，
理论可节省 23.4 GB；8 个文件未能完整处理。
```

摘要栏只显示以下主要指标：

- 扫描文件数。
- 成功处理数。
- 重复组数。
- 冗余副本数。
- 理论可节省空间。
- 处理失败数。

候选文件数、候选字节数、哈希完成数和扫描耗时属于扫描详情。扫描耗时由 GUI
控制器使用单调时钟记录，不放入核心文件算法。

### 8.2 统计口径

核心报告需要提供或能够稳定推导以下基础统计：

| 指标 | 定义 |
|---|---|
| 扫描文件数 | 文件发现阶段找到的普通文件数量 |
| 成功处理数 | 现有 `successfulFileCount` 语义 |
| 总逻辑字节数 | 成功读取元数据文件的文件大小之和 |
| 候选文件数 | 进入内容指纹阶段的文件数量 |
| 候选字节数 | 候选文件逻辑大小之和 |
| 哈希完成数 | 成功获得内容指纹的候选文件数量 |

结果摘要从重复组推导：

| 指标 | 定义 |
|---|---|
| 涉及重复的文件数 | 所有重复组成员数量之和 |
| 冗余副本数 | 每组成员数减一后求和 |
| 重复内容总逻辑大小 | 每组单文件大小乘成员数后求和 |
| 理论可节省空间 | 每组单文件大小乘冗余副本数后求和 |

所有字节累计都要防止整数溢出，并为零字节重复文件保留正确的组数和副本数。
“理论可节省空间”只是假设每组保留一个文件的逻辑大小估算，不代表已经释放或一定
能够释放的物理空间。界面工具提示必须说明该估算未考虑硬链接、稀疏文件和文件系统
压缩。只读 GUI 不使用“立即清理”或“已经节省”等误导性文案。

### 8.3 重复组主从模型

重复结果使用两个只读模型，避免在主表为同一组重复展示文件大小和组号。

重复组主表每组一行：

| 列 | 内容 |
|---|---|
| 重复组 | 稳定的界面组号 |
| 文件数量 | 组内文件数量 |
| 单文件大小 | 易读大小，保留原始整数排序值 |
| 冗余副本 | 文件数量减一 |
| 理论可节省 | 单文件大小乘冗余副本数 |

选择一个重复组后，路径详情模型显示该组所有完整路径。默认按理论可节省空间降序
查看，用户仍可按组号、文件数量和单文件大小排序。路径详情支持复制完整路径和打开
所在目录，不允许编辑、拖放、删除或移动。

模型持有 `std::shared_ptr<const ScanReport>` 或等价不可变句柄，并只保存组索引和
路径索引等轻量引用。易读大小用于 `Qt::DisplayRole`，原始 64 位数值用于专门排序
角色，精确字节数放入工具提示。SHA-256 默认隐藏，仅供诊断或复制。

### 8.4 失败模型

使用只读 `QAbstractTableModel`：

| 列 | 内容 |
|---|---|
| 处理阶段 | 发现、元数据或哈希 |
| 文件路径 | 完整路径 |
| 错误原因 | 用户可理解的系统错误文本 |

失败页签标题显示总数，例如“处理失败（8）”，并在表格上方简要汇总发现、元数据和
哈希三个阶段的失败数量。错误原因保持单行易读文本，完整系统信息可以放入工具提示。

表格只显示本次完整结束扫描的结果。局部文件失败属于 `Completed`，但状态摘要使用
“扫描完成，存在部分失败”；致命异常在窗口状态区域展示，不伪装成单文件失败。
取消结果不生成结论摘要，也不把部分重复组送入结果模型。

### 8.5 空结果和大量结果

- 没有重复项时显示“未发现重复内容”，不显示空白主表造成误解。
- 没有失败项时显示“所有已发现文件均完成处理”。
- 大量结果不为每个单元格复制完整业务对象，也不一次创建大量独立 QWidget。
- 路径列使用伸展布局和完整路径工具提示，不通过固定宽度适配 DPI。
- 新扫描开始时清空旧结果；完成后只接收当前扫描对应的不可变报告。

## 13. 风险与应对

| 风险 | 应对 |
|---|---|
| Qt 5.14.2 与当前工具链不兼容 | 阶段 10 先做最小验证，失败则单独评估 Qt 6 |
| GUI 阻塞或“未响应” | 完整扫描放入工作线程，主线程只处理界面 |
| 取消只停界面、不停核心 | 先完成核心 `std::stop_token` 传播 |
| 关闭窗口时线程仍运行 | 请求停止并等待 RAII 回收，禁止 detached thread |
| 工作线程直接更新模型 | 只通过 queued connection 回到 GUI 线程 |
| 哈希进度事件淹没 Qt 队列 | Worker 节流普通事件，阶段和完成事件强制发送 |
| 64 位字节数超出进度条范围 | 映射固定刻度，详情保留原始 64 位数值 |
| 大量结果造成重复拷贝 | 模型读取不可变报告，避免重复业务数据 |
| 理论可节省空间被误认为真实释放量 | 明确估算口径，并通过工具提示说明限制 |
| 取消或旧扫描结果覆盖当前结果 | 扫描标识校验，只展示当前完整报告 |
| GUI 侵入核心 | Qt 类型限制在 `apps/gui` 和 GUI 测试 |
| Qt 部署缺少插件或 DLL | 使用匹配版本 `windeployqt` 并在干净环境验证 |
| UI 开发带入删除功能 | v0.2.0 保持只读，删除移动单独规划 |
| 许可证遗漏 | 阶段 17 把许可证列为发布阻断项 |
